# Device control libraries and editors

Research checked on 21 November 2026. These are source-code and manufacturer-document findings, not hardware test results. The catalogue contains static descriptions and sendable controls; it does not run these libraries, transfer firmware, or implement a bidirectional editor. GitHub references in profiles pin the reviewed revisions. No third-party application code or artwork was imported.

## Behringer Mini and Micro instruments

Added PRO VS MINI, JT-4000 MICRO, JT-4000M MICRO, JT MINI, UB-Xa MINI, UB-1 MICRO, PHARA-O MINI, CZ-1 MINI, AKS MINI and D MINI. Each profile includes manufacturer artwork, original partial control diagrams, a connection inventory, manufacturer manual links and a verified CC subset. All new `portNames` arrays are empty because no physical USB port names were observed.

The [Gary909 editors](https://github.com/gary909) provide readable Web MIDI implementations for [PRO VS MINI](https://github.com/gary909/Pro_VS_Mini_Editor/tree/60544a34ed83b83b8575ccf53419f5e77ac19453), [JT-4000M](https://github.com/gary909/JT4000M-MIDI-EDITOR/tree/34d3c0b76b47785d034cbfbcd78c442bbeea4c57), [JT MINI](https://github.com/gary909/JT-Midi-Editor/tree/64e689bb92de67097f78538639af2c34ec3ed0fc), [UB-1](https://github.com/gary909/Behringer-UB1-Midi-Editor/tree/ccad99ace3cfbf8cc623eb40c76bb33af11d8d57) and [CZ-1](https://github.com/gary909/Behringer-CZ1-Midi-Editor/tree/2b4b8616b483e72eef1953c0eb29a64c08e54615). Their patch initialization and randomization send parameter values from the editor. That does not establish hardware state readback or saved-preset transfer. The CZ-1 source explicitly describes its assignments as needing adjustment against the real implementation; the manufacturer manual's CC table was therefore checked independently.

[SynthHUB](https://github.com/utajum/SynthHUB/tree/42be9fb911199990fc6a3350534e3f40dfe011ac) is broader: it advertises WebUSB/Web MIDI settings, patterns, presets and firmware support across 71 Behringer devices. Inspecting the device definitions gives a more useful boundary. For example, PROVS-MINI, JT-4000 and UB-1 have a `dumpreceive` setting and an update section, and their device drivers delegate to a generic driver. Other Mini definitions describe channel, clock, tuning, power-off and sequence settings. A listed model is evidence of an integration target, not proof of every advertised operation on that model. Its reviewed PROVS-MINI and JT MINI modules both report `hasSequencer = false`; this describes the editor's integration, not the presence of a hardware sequencer. No explicit repository license was returned by GitHub metadata during review, so no implementation code was copied.

The manufacturer's own manuals establish the important model differences:

- Original JT-4000 has USB MIDI and no separate MIDI input. JT-4000M adds a **3.5 mm TS MIDI input**, with a supplied DIN adapter, and additional documented CCs. These are separate profiles. The UB-1 also uses a TS input; a generic TRS MIDI adapter is not an interchangeable assumption.
- PRO VS MINI uses **0-99** for most sound parameters and **0-31** for portamento. UB-1 amp level is **0-9**. The profiles preserve those ranges instead of assuming every slider is 0-127.
- JT MINI, UB-Xa MINI, PHARA-O MINI, AKS MINI and D MINI have model-specific CC tables. Similar enclosures do not establish identical implementations. For example, filter cutoff is CC44 on these Mini models, whereas it is CC74 on the Micro and PRO VS models.
- AKS MINI has a shared sync input/output jack whose direction depends on the clock source. PRO VS MINI and CZ-1 MINI have sync input only. Analog sync is not MIDI.
- CZ-1's published table leaves many ranges unspecified. Its profile labels the controls as a subset of MIDI-byte parameters; it does not claim calibrated engineering units or complete multi-stage envelope support.

The CS MINI appears in SynthHUB's definitions, but no matching manual was present in its reviewed manual index. It was left out of this change pending verification. Existing TD-3, Model D and Neutron profiles retain their analog-panel limitations: a software configuration tool does not make an analog cutoff knob MIDI-controllable.

## Novation Circuit family

The [original Circuit Web Synth Editor](https://github.com/ewe2/circuit-web-synth-editor/tree/9e99c43bec7ca7366faaae12bd5112b1b7f31522) demonstrates editing beyond the eight macros using the synth's CC, NRPN and patch SysEx interfaces. The original profile now exposes additional oscillator-mixer, filter and amp-envelope CCs while retaining its existing macro IDs and channels. The archived [original programmer reference](https://github.com/ewe2/circuit-web-synth-editor/blob/9e99c43bec7ca7366faaae12bd5112b1b7f31522/resources/circuit-programmers-reference-guide-v1-0.pdf) confirms those assignments.

[circuit-tracks-tools](https://github.com/namirsab/circuit-tracks-tools/tree/f064cee7fd9ba755ed768b152a7734ef7e9b114a) is a Python library with an MCP interface. Its code separates ordinary CCs, NRPNs, patch construction and independently reverse-engineered project/file transfer. The latter requires framing, chunking, pacing and acknowledgements; the [protocol notes](https://github.com/namirsab/circuit-tracks-tools/blob/f064cee7fd9ba755ed768b152a7734ef7e9b114a/docs/sysex-file-protocol.md) are a starting point for a future librarian, not a reason to model file transfer as one slider. This repository reports an MIT license. The original web editor reports GPL-3.0; neither is a runtime dependency here.

The [official Tracks Programmer's Reference v3](https://fael-downloads-prod.focusrite.com/customer/prod/downloads/circuit_tracks_programmer_s_reference_guide_v3.pdf) confirms deep synth CCs on factory channels 1/2 and per-drum sample selection, level, pitch, decay, distortion, EQ and pan on channel 10. Drum sample selection is limited to 0-63. The Tracks profile now exposes these controls. Hardware channel changes require corresponding application remapping.

The [official Rhythm Programmer's Reference v5](https://fael-downloads-prod.focusrite.com/customer/prod/downloads/circuit_rhythm_programmer_s_reference_guide_v5_2.pdf) confirms per-track sample choice, playback mode, reverse, choke, slicing, sample boundaries, pitch, filters and mixer sends on factory channels 1-8. These are now mapped, including the documented small ranges for modes and toggles. Project program changes on channel 16 distinguish immediate from queued selection; the performance controls do not automatically change projects.

Circuit, Tracks, Rhythm and Mono Station must remain distinct protocol targets. Custom-firmware repositories can add different behavior, but those features are not stock-firmware catalogue mappings. NRPN sequences and complete patch/project read-write support remain integration work for a protocol-aware client.

## Korg Volcas

[Edisyn's Volca editor](https://github.com/eclab/edisyn/blob/9582f314e2b7ceadfb3d101c132ee50d6e736aba/edisyn/synth/korgvolca/KorgVolca.java) is a useful source for model-specific CC handling: Bass, Beats, Drum single/split modes, FM, Keys, Kick, NuBass and Sample/Sample2 modes have different maps. Its saved editor files do not mean that a Volca can return its current panel state or receive an equivalent hardware patch dump. FM2 support is not inferred from an FM1 editor entry. The [Volca Keys Web MIDI editor](https://github.com/rolodato/volca-keys-editor/tree/db79c162935cbc1a2b27da27c8331fe0c73109c0) is a smaller browser implementation of remote CC editing through a MIDI interface.

The [official Sample 2 factory multi-channel chart](https://cdn.korg.com/us/support/download/files/c19d48a599794ff64a25b553e951c2fb.pdf) supplies functionality missing from the previous profile: paired sample-number CC3/35, chromatic speed CC49, trigger delay CC50, loop CC68, reverb CC70, reverse CC75 and global reverb mix CC91 on channel 1. Those controls are now exposed. Sample-number sliders represent the two bytes separately; a client choosing a sample must send MSB then LSB as an ordered operation. The [single-channel chart](https://cdn.korg.com/us/support/download/files/a17dd932bd0a0836235db4919ba09295.pdf) is a different implementation and must not reuse this map.

[Volca-Poly-Sample](https://github.com/astriiddev/Volca-Poly-Sample) uses an Arduino MIDI processor to translate keyboard input into chromatic-speed CCs and distribute voices across Sample 2 parts. It requires matching samples/settings on parts 1-8, multi-channel mode and controller input on channel 16. This is additional functionality supplied by the adapter, not native chromatic note response, sustained note-off behavior, or a Sample 1 firmware feature. The [Sample 1 extender](https://github.com/denalena/arduino-volca-sample-extender) is another external translation approach, with its own channel scheme.

Korg's [official volca sample SDK](https://github.com/korginc/volcasample/tree/b0ed615f18c230a18b378d9ddc6a936971597e4e) is a C sample-and-sequence encoder with a BSD-3-Clause license. It generates SYRO **audio** for the sync input; it is not a MIDI SysEx sample uploader. Sample 2's USB librarian and community firmware are separate paths. Stock Volca Modular and Volca Mix have no MIDI input and were not added as MIDI device profiles.

## Integration priorities

1. Use the new CC mappings with the existing client and a MIDI output, preserving each control's channel and range. Keep the new profile selection manual until port names are verified.
2. For a future editor, add an explicit representation and sender for ordered NRPN or multi-CC operations, then protocol handlers for request/reply, checksums, timeouts and chunked dumps. Current static profiles cannot establish hardware readback.
3. Make optional adapters and firmware variants explicit. Do not advertise their capabilities as the factory instrument's implementation.
4. Verify on physical hardware before claiming tested device support. The checks in this change establish profile/schema validity, asset references, channel/range regressions and generated API behavior.
